# HostPapa accounts and utility sync

The site remains static Astro plus PHP. Accounts, sessions, email-code verification, Google sign-in, app documents, migration archives, and recovery copies live in HostPapa MySQL. Binder and Idle Slayer guest saves and Radius Map drawing are available without the backend.

## Setup

1. Back up the **existing Binder database** and rehearse restoration into a separate database. Accounts must use that same database so copying a legacy collection and revoking its key can commit atomically.
2. Verify PHP **8.4 or newer**, PDO MySQL, OpenSSL, cURL, mbstring, outbound authenticated TLS SMTP, and outbound HTTPS to Google. Use a patched supported runtime. The public entry points remain parseable on PHP 7.4 and return an unavailable response before loading modern code; they do not upgrade the server automatically.
   HostPapa's handler `application/x-httpd-alt-php84___lsphp` was verified in an isolated probe on November 17, 2026 with PHP 8.4.27, all required extensions, 128 MiB memory and an 8 MiB POST limit. The portfolio uses scoped `.htaccess` directives to select it for the account, MCP, Contact, Radius Map geocoding and Binder entry points. Use these directives to scope changes to this site. Recheck the registered handler when moving hosts.
3. Install the root Composer lockfile before building. The account code loads `public/reporting/vendor/autoload.php` independently of the optional reporting bootstrap. Google signature verification also requires the pinned `phpseclib/phpseclib` package.
4. Copy `config.example.php` to `~/private/accounts.php` outside `public_html`. Use owner-only directory/file permissions (`0700`/`0600`), a new random secret, and a dedicated domain mailbox. Obtain actual SMTP hostname, TLS port, and credentials from cPanel rather than disabling certificate checks. An absolute trusted `ACCOUNTS_CONFIG` path may override the default.
5. Apply the additive schema using a separate setup user: `php server/accounts/migrate.php /absolute/private/accounts.php`. The CLI migration is repeatable and preserves existing tables and data. The Binder schema ledger remains version 1.
6. Use a runtime user with SELECT/INSERT/UPDATE/DELETE on the new account tables; it also needs SELECT/UPDATE on `pokedex_binders` and SELECT on `pokedex_binder_clients`. It needs no DDL or global privileges. Keep the legacy Binder runtime credentials separate.
7. Register a dedicated Google web OAuth client and exact callback `https://austingarrod.ca/api/v1/auth.php?action=google-callback`, requesting only `openid email`. Configure its consent branding and production publishing. Store its secret only in the private configuration.
   The public account disclosure is `https://austingarrod.ca/account/privacy/`; use the site homepage and that URL for the client branding/privacy configuration.
8. Deploy with both `enabled` and `migrationEnabled` false. Verify headers, private-file protection, backups, runtime, SMTP delivery, and Google login before enabling accounts, then migrations. The FTP artifact contains no runtime configuration or database dump. Public `/_*.php` helpers are denied by the API's scoped `.htaccess`.

For private live checks, keep those public switches false and set the private `preview` block's `enabled` flag plus the operator's exact server-observed `REMOTE_ADDR` in `addresses`. Only those IP literals receive an enabled account service; login, CSRF, origin, account ownership and all normal validation still apply. Preview migrations additionally require `preview.migrationEnabled: true`. Forwarded headers, CIDR ranges, hostnames and missing addresses never grant access. Verify the disabled response from a separate, unlisted connection before testing. Use an actual client address rather than a shared reverse-proxy address; disable preview and clear its addresses after the public rollout.

The loader refreshes this private configuration independently of OPcache's timestamp interval, including public and preview disable switches. Active OPcache must permit its status/invalidation APIs; an unverifiable cache refresh fails closed. Verify disabled responses after every rollout/rollback configuration change before proceeding.

Do not record auth request bodies, cookies, codes, Google tokens, key headers, email addresses, or saved state in error reporting or session replays. Google authorization-code responses use `response_mode=form_post`, so codes and state stay out of normal callback request URLs. A separate ten-minute Secure/HttpOnly `SameSite=None` OAuth proof cookie binds that POST to its original account/preauth session; the main session cookie remains `SameSite=Lax`. Callback processing requires Google's exact Origin, the single-use state, proof, live original session, PKCE and a verified token nonce, then clears the proof cookie and redirects to a clean account URL. GET callbacks and query-bearing callback secrets are rejected. Verify that hosting/WAF diagnostics omit auth/sync request bodies and sensitive headers before enabling accounts; disabling cPanel raw-log archiving does not disable server access logging. Server diagnostics contain only a generated request ID. Auth/sync responses always use `Cache-Control: no-store` and must never enter a service-worker cache.

## Protocol and preservation

`/api/v1/auth.php` provides session discovery, explicit login bootstrap, emailed-code start/verify, Google start/callback, logout, and logout-all. Codes last ten minutes, allow five attempts, and have a sixty-second address cooldown. Their keyed hashes and opaque session-token hashes stay server-side. The host-only session cookie is Secure/HttpOnly/SameSite=Lax, with thirty-day inactivity and ninety-day absolute expiry. Ordinary auth and sync mutations require the session CSRF token and exact configured Origin. Auth mutations also lock and recheck their originally observed session inside their transaction; a retired, expired or mismatched snapshot fails before changing challenges, identity, sessions or action rate counters. Authentication mutation cookies are published only after commit.

Session discovery with a present retired/invalid cookie returns signed-out state with `requiresBootstrap: true`, an empty CSRF token and no `Set-Cookie`. Discovery and background refresh never replace that cookie automatically. A deliberate email/Google login or login retry can POST an empty JSON object to `auth.php?action=bootstrap`: this action requires the exact site Origin and JSON, with a CSRF exception because no live preauth session exists. It rechecks the request cookie and returns a valid current session unchanged, or creates a fresh preauth session for an absent/retired cookie. Verification and logout never bootstrap automatically. Google's provider form POST is the other CSRF-token exception, using its exact provider Origin and the separate proof/state/session/PKCE/nonce checks above.

`/api/v1/sync.php` requires a signed-in session **and** `X-Account-ID` matching it on every read and mutation. Documents are registered by `(app, document)` and owned by immutable account UUID. The registry includes Binder `binder` and `master-sets`, Idle Slayer `progress`, `intentions`, `checkpoints`, `comparison`, and Radius Map `measurements`. Each document has versioned validation and a byte limit. Unknown Slayer catalogue IDs and canonical decimal strings are retained. Radius Map sync stores names, location labels, exact saved centres, distances, visibility, and timestamps in a version 1 library up to 4 MiB.

Writes use revision preconditions, device sequence acknowledgments, and operation IDs. Exact operation replay returns current state without applying an old mutation again. An accepted write with identical state acknowledges its sequence at the existing revision. A stale revision returns `409` with the current document, preserving both copies. Devices retain their own durable outbox and must review a real divergent state before retrying.

Radius Map opens the account library on sign-in. Its first synced save creates the measurements document at revision 1. The device keeps its account library and pending edits in IndexedDB. Per-measurement conflicts use the shared recovery flow described below.

Migration uploads each selected/device variant separately under one durable migration UUID, keeping individual requests within existing document limits. Reusing an ID with different staged content is rejected. First adoption commits all documents for the app together. Later `purpose: "conflict"` commits can cover a subset of existing documents, require both device and selected variants, and cannot claim a legacy key. Stages remain available for exact replay after a lost commit response.

Binder adoption stages both the device and selected copies of its National Dex and named set collections. Existing National Dex clients may submit a Binder-only manifest. The master-set document has its own 4 MiB limit, revision, outbox and recovery history. Key claims are retired. Existing migration archives and tombstones remain available to their account owners. See [private-key retirement](../pokedex-binder/README.md).

Public Binder links live in `accounts_binder_shares`. Apply `server/pokedex-binder/shares.sql` before deploying sharing code, and verify the account runtime can read, insert and update the table. An authenticated owner publishes or revokes a link through sync. The public route reads only that binder’s display data. Its URL fragment and request header contain the link token and must stay out of diagnostics. A synced removal revokes the link in the same transaction as the document update. Preserve the share table on rollback.

Recovery list/read/restore/delete operations check ownership. Routine sync keeps a checkpoint before the first changed sync per document on a UTC date. The most recent three checkpoint dates are retained, with the first pre-sync copy retained on dates that have older per-edit history. Checkpoint creation and pruning share the document write transaction. Explicit replacement writes carry `preservePrevious: true` in their frozen outbox and keep the prior live save separately. Migration, conflict, restore, replacement, and assistant copies are kept until explicitly deleted. Do not restore an older production database over newer saves as an application rollback. Keep account tables and key revocations when rolling back frontend assets, and preserve any newer device outboxes.

## Local verification

Run `node scripts/test-accounts-api.mjs` with `ACCOUNTS_TEST_DSN`, optional `ACCOUNTS_TEST_USER`/`ACCOUNTS_TEST_PASSWORD`, and optional `PHP_BINARY`. The DSN must use a loopback host. The harness creates a random `accounts_test_*` database and drops only that database; it uses real production handlers, two PHP processes, and a local SMTP sink to read and verify actual emailed codes. Its fixtures, configuration, and logs remain under ignored `tmp/`.

The harness checks CSRF/origin/account isolation, expired/reused/brute-forced codes, Google state/PKCE/cancellation, locally signed RSA tokens through Google's production verifier, concurrent writes, exact replay, migration revocation/archives, partial conflict resolution, large Slayer state, and recovery. It never contacts Google or production data. Live Google consent/callback, mailbox delivery, and hosting behavior still need separate owner-operated smoke tests before enabling production.

`npm run test:accounts:browser` uses the built `dist/`, an isolated database, and a loopback SMTP inbox to verify the account page, all three utilities, second-browser sync, recovery, and logout. It blocks external traffic and keeps screenshots and results under ignored `output/accounts-browser/`.

`npm run test:accounts:large` exercises a valid progress document near the existing 4 MiB portable limit in native Chromium. It checks migration readback, unchanged guest records, offline reload, frozen retry operations, and failed IndexedDB transactions. Its isolated database, local SMTP inbox and blocked external traffic follow the same restrictions; diagnostics stay under ignored `output/accounts-large-browser/`.

## Adding another utility

Register its document names and byte limits in `ACCOUNTS_DOCUMENT_LIMITS`, add a strict validator in the utility adapter section of `_validators.php`, and implement its browser storage/migration adapter using `packages/accounts/client.ts`. Complete adoption manifests are derived from that registry; authentication, sessions, CSRF, revisions, recovery, and the API routes do not change. Local entry routes under `/utilities/<slug>/` or `/apps/<slug>/` work as login return destinations. Add validation fixtures and a real migration/recovery browser scenario before enabling the adapter.

The browser adapter must retain originals, keep an immutable in-flight request until acknowledgement, use per-document device sequences, fence late responses by account/resource/revision, and switch its active namespace only after durable commit and checked readback. Missing, malformed and deliberately cleared documents are distinct cases. The server accepts only registered schema versions and never assumes an arbitrary JSON object is a valid save.

Idle Slayer account documents, outboxes, migration journals and recovery records use IndexedDB. Guest localStorage records keep their existing keys and formats. Account edits and their frozen outbox share one record and one transaction; the UI acknowledges a device save only after transaction completion and readback. Keep these records out of localStorage: several recovery copies of a valid 4 MiB document exceed its ordinary quota. Storage failure must leave the open visit exportable and must not authorize an upload or a switch to another account.

Authentication discovery and mutations share a same-origin Web Lock across tabs to prevent a stale response from replacing a newly authenticated cookie. Account sign-in/sync requires a browser with Web Locks on HTTPS; unsupported browsers keep guest saves and backups available.

## Utility admin

Open `/account/admin/` with an authorized utility account. The dashboard counts account registrations, live sessions, and current saves. Recent utility activity counts accounts with a changed save in the last 30 days. The directory opens an account's sign-in metadata, current saves, client counts, recovery copies, and Binder stock-alert preferences and send attempts when available. JSON downloads contain the complete stored save. Guest saves, unsynced edits and Screen Cut Calculator settings remain on their original devices.

The API opens only with live accounts and a private allowlist. It uses the existing account database and requires no schema change. Provision access after verifying the existing operator's account UUID against their verified email:

1. In the same private directory as the active `accounts.php`, create an empty `utility-admin-audit.jsonl` owned by the PHP runtime's account and writable by that owner. Preserve the contents if the file already exists.
2. Create `utility-admin.json` with `{"operators":["<existing account UUID>"]}`. Keep both files outside the webroot and set their permissions to `0600`.
3. Recheck the deployed page while signed out and with an unlisted account. Verify the allowlisted account can open the overview and an authorized test save. The API checks the account UUID, same-origin POST, session and CSRF token for every request.

Each successful read records its UTC timestamp, operator UUID and action, plus the account and save UUIDs where applicable. The audit excludes search terms, email addresses, and save content. Keep the audit file private. To rotate it, prepare an empty owner-writable file with mode `0600` in the same private directory, move the old log to its archive name, and rename the prepared file into place. Access pauses if the audit path is absent. To disable admin access, remove the allowlist or set its operators to an empty list. The next request reads the changed file.

The accounts API and browser suites exercise utility admin with local accounts and a disposable database. Browser screenshots use synthetic data under ignored `output/accounts-browser/`.
