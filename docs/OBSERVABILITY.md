# Portfolio observability

Project: [AustinGarrod.ca / project 8](https://reports.garrod.house/garrod-house/issues?project=8), organization `garrod-house`, slug `austingarrodca`. The destination is GlitchTip, using its Sentry-compatible ingest, artifact-bundle, logs and transaction APIs. There was no existing Sentry SDK, DSN, upload step or historical project integration in this repository. The Sentry reference in portfolio case-study content describes another product and remains intact.

## Runtime coverage

`src/reporting/browser.ts` initializes the compatible Sentry browser 10 SDK for every production-built page, including standalone utility layouts. Default integrations preserve unhandled errors/rejections, linked causes, click/navigation/console/fetch/XHR breadcrumbs, request context and browser/OS/device context. Explicit integrations record console warnings/errors as issues, structured console logs, failed HTTP 429/5xx responses and pageload/navigation performance. Resource-load and CSP failures are reported. Connectivity, page, utility operation and calculator state provide reproduction context. Map tile failures produce one issue per page plus diagnostic counts; measurement storage/CRUD/recovery, geocoding, geolocation and PWA setup failures retain their operations and original causes where available. Saved measurement documents remain browser-local.

Both PHP endpoints load `public/reporting/bootstrap.php`. The Composer-locked Sentry PHP SDK captures exceptions, warnings and fatal errors with original causes, source excerpts, request/runtime context and a request transaction. Contact instrumentation distinguishes rate-limit infrastructure failures from mail rejection and preserves the underlying mail warning/exception. Geocoding distinguishes cache, locking, missing cURL, transport, upstream status/rate limits and invalid JSON failures. Mail, upstream HTTP and rate-limit waiting have child spans; response/result logs supplement failures. `X-Request-ID` ties browser errors to PHP events. Geocoding fetches propagate trace headers only to this site's API; the native contact form sends the browser trace in a hidden field. No trace headers are added to map tiles or Nominatim.

Errors and transactions are sampled at 100%. Logs are enabled without an SDK-side sample filter. The project was created with no event throttle and its key has no rate limit. The breadcrumb limit is 100, normalization depth 6, and PHP reporting transport deadlines are one second to connect and two seconds overall per envelope. Reporting failures fall back to PHP error logs and do not replace endpoint responses. There is no persistent PHP telemetry queue on shared hosting; blocked egress or outages can lose reports. Browser blockers/offline conditions can also prevent delivery.

The geocoder retains its pre-existing no-raw-query-logging rule: its query is removed from diagnostic URLs, breadcrumbs, events and transaction requests. Other reporting context is retained, including default SDK request/device information. API tokens remain in protected local credentials or GitHub secrets. The public ingest DSN is intentionally present in browser and PHP code.

## Build and deployment

1. Install Node dependencies with `npm ci` and the PHP bundle with `composer install --no-dev --prefer-dist --optimize-autoloader` (PHP 8.1+, cURL and mbstring, preserving the existing geocoder's PHP minimum).
2. `npm run build` generates a shared browser/PHP identity, checks/builds Astro with hidden source maps, injects debug IDs and then creates the Radius Map service worker from the final JavaScript bytes. `PUBLIC_REPORTING_RELEASE` overrides the default `austingarrod-ca@<GITHUB_SHA or local HEAD>`; `PUBLIC_REPORTING_ENVIRONMENT` defaults to `production`.
3. With a GlitchTip token in `SENTRY_AUTH_TOKEN`, run `npm run reporting:upload`. It explicitly binds the destination, organization and project, removes ambient Sentry DSN configuration, and removes maps from `dist/_astro` only after a successful upload. Debug IDs identify exact bundles even across builds of the same commit. Sentry CLI's `--wait` processing polling did not complete on this instance, so server-side symbolication is verified by event readback instead. All application scripts remain external so Header and Contact also have source maps. The BaseLayout import-only shim has no original source map; its imported reporting module does.
4. Generate the deployment manifest and run `npm run verify:dist`. The verifier requires the PHP SDK, generated identity, reporting directory access rule and both reporting CSP entries. Upload `dist/` contents over FTPS. `/reporting/.htaccess` denies HTTP access to bundled dependencies/configuration; PHP includes continue to work.

The deploy workflow builds the PHP bundle, runs tests/build, requires `REPORTS_AUTH_TOKEN` and a successful source-map upload before FTPS, then verifies the final output. This secret currently uses the existing protected reporting token (project read/write/releases, org read, event read); the current API token cannot mint another token. No token is committed. `scripts/reporting-ops.ps1 -Action Inspect|Configure|Upload|Verify -CredentialPath <protected-token.dpapi>` provides local administration without echoing credentials. CI never reads the local credential. Rotate the GitHub secret when rotating that token.

Workflow failures send a deployment-environment event with the failed step and GitHub run/commit link. Errors before checkout or Node setup, runner outages and reporting-service outages may prevent this fallback. Existing Sentry projects/history are untouched.

For local PHP configuration, trusted `REPORTING_DSN` may override or disable ingestion, `REPORTING_ENVIRONMENT` overrides the PHP environment, and `REPORTING_DEBUG=1` enables SDK transport diagnostics to stderr. These are server environment settings, never request parameters. Windows development uses the native CA store; TLS verification stays enabled.

## Verification

`npm test` exercises the existing utility contracts. For browser/PHP diagnostics, build with `PUBLIC_REPORTING_ENVIRONMENT=reporting-verification`, then run `node scripts/verify-reporting.mjs`. It launches only a localhost PHP server and headless browser, disables mail, isolates temporary rate-limit/cache state, mocks analytics/map traffic and intercepts browser ingest. PHP ingest is disabled by default. Add `--deliver` deliberately to deliver synthetic verification events to project 8. The script refuses a production-environment build. It exercises causes, unhandled errors/rejections, storage failure, resource failure, geocoder failure, trace propagation and contact mail failure, plus eight local routes, calculator output and the mobile menu. Evidence stays in ignored `output/` files. Server readback and source-map processing are separate checks from local payload assertions.

Do not point automated browser/API tests at the live portfolio. After deployment, manually open the site/utility/contact pages and use ordinary browser interactions to confirm release/environment delivery and HostPapa PHP behavior. A local mail-disabled test does not prove HostPapa mail delivery.

## Capability limits

GlitchTip accepts browser/PHP errors, structured logs, transactions and uploaded JavaScript source maps. Automatic session envelopes are disabled because GlitchTip does not support Sentry Release Health sessions. Sentry Replay, profiling and arbitrary attachments are not assumed supported; existing Umami usage/replay instrumentation remains separate. PHP source context is captured from deployed files and does not need JavaScript maps. PHP parse errors before the bootstrap and web-server/FTPS outages cannot be caught by the in-process SDK. Third-party cross-origin errors may have browser-limited stacks.

Retention is an instance-wide setting, not a project sampling knob. This migration does not change retention for other products or claim an unverified value. Operators should review the instance's error/transaction/log retention, disk budget and ingress limits when volumes grow; current project/key ingest limits do not downsample this site. [GlitchTip logs documentation](https://glitchtip.com/documentation/logs/) describes retention configuration; [JavaScript setup](https://glitchtip.com/sdkdocs/javascript/) and [CLI documentation](https://glitchtip.com/documentation/cli/) describe the supported formats and maps.
