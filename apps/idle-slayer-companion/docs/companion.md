# Companion architecture and player contract

Idle Slayer Companion is a static React/TypeScript application. Its seven routes are the Overview root plus `ascension/`, `achievements/`, `crafting/`, `quests/`, `bestiary/`, and `divinities/`. Every route has a built HTML entry for direct links and offline reopening. Navigation does not reload the application or discard the mounted Ascension canvas.

The slim header carries the "Austin Garrod" link, the `Utilities / Idle Slayer Companion` breadcrumb (its last part returns to Overview), a short save note, "Unofficial" and one **Data** button. The Companion navigation owns **Privacy & tracking**, **About & sources**, and **Install & offline**; the rail's collapsed state is a device-local preference (`idle-slayer-companion.rail.v1`). **Map help…** is available from About & sources and the map's View tools. The embedded map omits its former app-wide footer and duplicate app-wide menu actions. The map toolbar groups Ascension tools as View, Plan and Record; files, QR transfer, account and clearing live in **Data & backup**.

Data & backup is one dialog for every system: Import save…, Back up everything (one bundle of the four documents, `domain/backup-bundle.ts`), one Restore from a backup file that recognises the bundle, each single document by its `format`/`kind`, or the original map JSON by shape (`detectBackup`), map-scoped QR send/receive, Account & sync, Clear (Ascension or everything, each previewed) and **Advanced: single files** with the separate exports and their original labels. The checkpoint and comparison sessions are owned by the app shell, so their exports and restores work from any section; Ascension-only hand-offs (map JSON restore, QR transfer, clearing the map, opening checkpoints or the saved comparison) navigate to the map and run through its guarded action controller, preserving purchase/transfer previews and save-before-reload protections. When a reload is blocked by reference recovery, Privacy & tracking offers **Review checkpoints** and **Review saved comparison**. The shared Undo/Redo also uses that controller while the map is mounted, retaining transfer layout restoration, pending-preview invalidation, feedback and camera handling across sections. Change confirmations appear as a status message in the status row next to a briefly highlighted Undo. On short phone map views (at most 600 × 650 px), the status row is hidden to preserve the inspection canvas and Undo/Redo move into the Record tools. Recovery controls stay visible.

Tracker sections list visible entries grouped by system and category (`companionGroups`, with per-group recorded and complete counts), one row per entry that expands in place into the full entry. Internal category identifiers such as `PowerLevel` are shown as words (`companionCategoryLabel`) without changing stored categories or filters. Groups and expanded entries are visit-only view state; navigating to an entry opens its group, expands it and focuses its `companion-entity-<system>-<id>` element. Every row follows the same visible projection as before; grouping adds no hidden counts.

When a section has nothing visible, its empty state offers **Show all entries**, which turns on the same Show spoilers setting the map uses (one visibility projection), and **Import a save**. Overview shows **Start here** on a first visit and, afterwards, visible-only "X of Y" counts per section and the next suggested upgrade with its wiki attribution. The migration notice appears only when arriving with `?migration=1` (always in the legacy build). Catalog wording that reads as internal jargon is replaced at render time (`companionDisplayText` in `companion-view-model.ts`); the hash-locked catalog text is unchanged.

## Actual observations

`CompanionProgress` contains the existing Ascension profile and seven typed record collections: achievement, craft, material, quest, village, enemy, and divinity. Each collection has an explicit tracked state. A missing field means **unrecorded**, not false or zero. Decimal counters remain strings; calculations use integer arithmetic. Observation timestamps describe recording in this utility, not authenticated gameplay dates.

The new storage key is `idle-slayer-companion.progress.v1`. Its device wrapper contains a validated progress document and the exact legacy profile baseline. Startup reads legacy map data without writing, deleting, or mirroring it. The first deliberate change writes the new envelope under the original profile write lock. Reads and writes check both old and new baselines; a stale older tab cannot silently overwrite the Companion. When a changed legacy copy is detected, Backup offers an optional normalized legacy-map export before acknowledgement, preserving unknown IDs without merging or rewriting that old copy. Invalid new storage never falls back to an older map profile. Failed saving leaves the visit usable and exportable.

The session has one bounded 20-action Undo/Redo history across all actual observations. Its map adapter projects the existing profile/history APIs without leaking companion-only item records into old map JSON or QR. Known shared craft/Village completion uses the same milestone ownership fact as Ascension. Removing that fact previews dependent Ascension removals using the existing native rules, preserves valid alternate paths and retained purchases, and applies the correction with one Undo. The map catalog must be available before removing recorded item ownership while Ascension purchases exist. Recording observations never consumes stock or infers an earlier boss/NPC event. Map-only operations preserve companion observations and facts outside their reviewed map scope.

## Rules and projections

Both catalogs load and validate independently. An unavailable map does not disable manual achievement tracking; an unavailable companion catalog does not disable the tree. Native import and actual reset require both reviewed catalogs. Retrying or repairing app files uses the same save/export/cancel protection as a privacy reload.

Companion requirements evaluate to met, unmet, or unknown. Unknown unsupported game conditions stay hidden by default. The shared visible projection governs module cards, search, counts, detail references, goal labels, shopping lists, and operation previews. Turning on spoilers permits reference browsing but does not make an unknown purchase gate met. Achievement names follow the native locked-title policy until earned; platform labels refer to native registration flags. Only reviewed UA achievement counters claim numeric progress. Four enemies excluded by the native Bestiary remain conservatively hidden.

Divinity selection is recorded separately from effective activity. Activity depends on the native global activation gate; Dark availability also has reviewed item/upgrade and boss gates. Bestiary mastery sums the exact native evolution family; it remains unknown until every required count is recorded. Recipes retain static material, coin, and Divinity Point costs. Shopping lists aggregate only visible planned recipes with exact integer arithmetic, distinguish unknown inventory from a deficit, and never spend resources.

## Imports and actual resets

The global importer decodes a selected save once, validates the versioned adapter, and previews all supported changes against the current visible universe. The preview leads with a summary table (recorded and complete counts per section, now and after, from the tested `summarizeCompanionChanges`), keeps per-section details collapsed and holds its confirm and cancel actions in a sticky footer; the file form is hidden while a preview is open. A confirmed 7.3.4 import is one replacement and one Undo action. A legacy 7.2.0 import replaces only reviewed map fields and keeps companion modules. Neither imports unrelated native preferences. Inputs are transient and never uploaded or stored as raw saves. Native purchase history is absent, so the reviewed synthetic retained-ownership baseline remains explicit.

The actual Ultra Ascension button uses `planCompanionUltraAscension`, combining the native tree plan with reviewed quest/shop reset and retention rules, automatic quest rewards, item facts, UA achievement updates, and conditional counters. All effects apply atomically. A missing input clears dependent outputs to unrecorded instead of making up a count. Ordinary manual completion/claim/craft edits do not run these side effects. Tree-only hypothetical plans stay separate and never simulate the other modules.

Checkpoint operation context is still tree-only. A Companion reset may explain a tree transition only through visit-local proof of the full reviewed native transition plus an exact projected tree-plan match. Imports, portable snapshots, names, and a higher UA count cannot establish reset history.

## Intentions and references

The independent `idle-slayer-companion.workspace.v1` document contains at most 20 typed goals and 100 recipe quantities. It migrates old map goals without startup writes and checks its exact old/new baselines under coordinated writing. Recovery requires a reviewed draft and current version; a later write invalidates that draft. Goals and plans never enter progress Undo and survive save imports and actual resets. They have their own JSON export/restore and are included in Back up everything.

Four named Ascension checkpoints and the four-entry saved upgrade comparison retain their existing separate formats, storage, recovery, and spoiler rules. Back up everything bundles them with progress and intentions (`idle-slayer-companion-backup`); restoring a bundle reviews each part and applies each through its own existing preview, so no document is replaced without its usual confirmation. Legacy map JSON and map/layout QR readers remain supported and explicitly map-scoped.

## Privacy and limits

New module contents and all global operation/recovery dialogs are replay-blocked. Existing visible map progress can appear in recordings as disclosed. No new telemetry provider or progress payload was added. Tracking settings, layout, and installed-app caches remain independent from progress and intentions.

Daily/weekly quests, Armory, Minions, SP-balance simulation, Stone allocation, cloud-save downloads, and automatic game-file access are outside this release. Optional unified website accounts now sync the four normalized documents after reviewed, recoverable migration; selected native save files remain local. Unsupported NPC/task conditions remain unknown. Physical device installation and live production behavior require separate evidence. Native extraction details and refresh commands are in [companion-native-review.md](companion-native-review.md).

## Optional website account sync

Account & sync uses the site's shared email-code/Google login. Guest operation, offline files, existing transfer formats, and original local keys remain available. Connecting requires a per-document choice when browser and account copies differ. Progress, intentions, checkpoints and underlying saved comparison connect together only after staged server commit and validated readback. Layout and tracking preferences remain device-local.

Before connecting or resolving a conflict, the browser writes and verifies an exact raw recovery snapshot in IndexedDB. Original guest localStorage keys are never deleted or rewritten by connection. Account data, acknowledged revisions, client identity and pending mutations share one atomic, account-specific IndexedDB record; migration journals and recovery snapshots are separate records in the same database. This avoids multiplying large supported documents inside the origin's small Web Storage quota. Edits use one account write lock and reload the latest durable account record before checking baselines. Network requests use a client bound to that immutable account ID. Signing out or switching accounts invalidates late responses and mounts separate domain sessions. A failed save, unavailable storage, or changed migration source prevents activation and leaves originals exportable.

The synchronous account read cache is hydrated before mounting account sessions. Document writes are awaitable: the domain adopts its saved baseline only after the IndexedDB transaction completes and exact durable readback succeeds. Quota errors, aborted transactions and read failures keep the previous durable record and exportable in-memory visit; they never turn a failed write into a Saved indication. IndexedDB commit notifications refresh other tabs under the same account lock. Cached copies belonging to a previous login remain explicitly labelled for recovery when unsaved state prevents a safe switch, and cannot upload to the new login. Unreleased localStorage account records are copied into IndexedDB only when absent there, verified, and retained at their original keys.

Automatic sync uses revision checks and idempotent durable mutations. Divergent copies require review; no union, maximum-count rule or last-writer overwrite is used. Both device and selected snapshots are staged before conflict resolution, and account recovery retains the displaced version. Comparison syncing retains its underlying validated IDs; existing spoiler filtering governs presentation. Native selected save bytes, auth payloads and sync contents never enter telemetry or offline caches. The frozen legacy-migration build has no account UI or account API calls; its guided export/import instructions are unchanged.
