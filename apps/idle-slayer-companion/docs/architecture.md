# Architecture and progress contract

[Technical reporting](reporting.md) lives in browser adapters and startup, outside game rules and persisted documents. GlitchTip uses release-bound source maps and the existing Pages pipeline; no application backend is added.

The Ascension sections below remain the tree-specific contracts. Tree checkpoints, comparisons, route plans, and hypothetical UA plans have not become full companion snapshots.

Expanded inspector values wrap between comma groups, and copying uses the original decimal string with an honest manual fallback when the clipboard API rejects access. Native comparison/eligibility arithmetic and profile/schema contracts remain unchanged.

`MapApp.tsx` coordinates player actions and derived visible graph state. Rendering and browser subscription lifetimes have focused boundaries: `UpgradeCard.tsx` defines fixed map tiles and renderer registrations; `MapDialog.tsx` owns native-dialog focus restoration and private feedback presentation; `useProfileSession.ts` observes one atomic `ProfileSessionState` snapshot instead of mirroring its fields into independent React states. Domain transitions stay in `domain/`; prior-UA history entry uses the independently tested `planPriorAscensions` helper. The initial analytics context is installed before session initialization can report a storage failure. Existing spoiler visibility, confirmation, focus and session-only history contracts remain unchanged.

`public/catalog.json` contains the complete reviewed catalog. Native IDs identify upgrades; titles may repeat. Decimal string costs format with `BigInt`, and native positions remain unchanged in the catalog. The Game layout converts Unity’s positive-up Y axis to the browser’s positive-down Y axis; pairwise game placement is preserved. The Web layout arranges the visible graph independently. `catalog.ts` validates structure, references and reachable purchase/reveal paths before rendering. Build tests compare records and icon bytes against the independently reviewed native registry receipt.

`recent-navigation.ts` stores a bounded most-recent-first set of up to 20 inspected stable IDs in mounted React view state. Every deliberate selection adds or moves its ID; overview/refocus and keyboard browsing without selection do not. Closing details retains the list. `RecentUpgrades` receives only the current shared visible IDs and identities; rendering filters synchronously and a layout effect discards entries that become hidden, so a later spoiler/reveal change cannot resurrect old context. Returning closes the dialog and uses the existing center/detail-focus path without changing purchases, profile Undo, backups, URLs or persistence. Queued selection centering also checks the latest visible IDs and layout before moving the camera. The list can be cleared and disappears on reload. Its DOM is replay-blocked; trail contents and new events are not collected. Returning uses the existing current-visible selection event.

Recent-dialog guidance, identity text and its bounded Clear button wrap within the available content width, including enlarged browser text and differing system-font metrics. The list keeps the native dialog's vertical scrolling and ordinary keyboard controls.

Opening recovery, another panel or an action preview closes the Recent dialog while retaining its inspection list. Recovery controls shared with other dialogs must leave one correctly named native dialog active, including when unsaved local progress conflicts with another tab.

## Rules and spoilers

The exact `progress-checkpoints` v1 envelope rejects unrelated fields, dates and operation claims. Catalog migration updates each profile's revision using the existing validator, preserving unknown ownership and milestones plus captured revision. The active profile key, portable v1 profile schema and session Undo/Redo remain unchanged. Export/restore is explicitly separate; deletion and full-list replacement require review.

Checkpoint reducer commands capture the session's current adopted collection, with a vault-version guard rather than a render's stale full list. Capture reads the active profile synchronously and normalizes/clones it before returning. Rename/delete/restore/recovery drafts retain their original version; newer adoption invalidates them before use. A dedicated exclusive `ifAvailable` Web Lock checks the exact accepted saved text inside the callback before writing. External clean changes are adopted without writing; dirty/pending/invalid changes keep exportable memory state and checked recovery. Failed/unavailable/held coordination keeps the collection usable. Latest-read and unmount guards suppress late file outcomes. Removing all checkpoints is an explicit supported collection, not deletion of active progress.

`ProgressComparison` has a read-only reference purpose; its existing replacement/Cancel/Undo wording remains the default. Both checkpoint sides project through the live active profile's shared visible graph, so old spoiler settings do not broaden identities, totals, milestone lists or relationships. No original denominator is retained or interpreted as gain/loss. Generic visible ownership/activation summaries and paginated details preserve stable duplicate IDs and omit unknowns. Hidden-only/unknown-only differences produce the same no-visible-difference explanation. Native rules and recommendations consume only the active profile.

`domain/checkpoint-history.ts` matches canonical native state (including unknown facts, excluding only catalog revision) against the actual current visit's bounded chronological Undo/Redo chain. Both references must occur uniquely. A recorded `ultra_ascension` step must also equal `planUltraAscension` output; matching prior-UA/import/restore labels never imply reset. Cleared/activated counts are current-visible and forward-only, with reverse comparisons explicitly marked. No chain or action proof is persisted or accepted from a file. After reload, external progress replacement, truncation or ambiguous repeated states, causal context is unknown. This deliberately supplies portable state comparisons without claiming recovered gameplay dates or a complete activity ledger. The entire checkpoint UI and file input are replay-blocked; no checkpoint telemetry event or payload is added.

Purchase and reveal explanations preserve nested AND/OR grouping with parentheses whenever the operator changes. The pure formatter retains caller-supplied visible/hidden leaf labels and activation notes without changing rule evaluation.

`requirement-view.ts` projects requirements through the shared visible graph for details and blocked purchases. The view explains that visible portions alone are shown and native gates still apply. AND/OR grouping among visible portions remains explicit. A return control retains the original visible target while reviewing prerequisites and creates no purchase plan; returning requires a fresh purchase preview. External progress changes or hiding the original target invalidate that context.

`rules.ts` evaluates explicit AND/OR, owned, active, milestone and previous-Ultra-Ascension expressions. Purchase and reveal predicates are separate. Visible locked nodes remain present. Search ignores case, accents and apostrophe variants. Hiding spoilers closes an inspector that is no longer revealed. Spoiler toggles preserve the current viewport translation and zoom in both layouts: graph changes do not request camera centering, queued/animated camera work is stopped, and a closing inspector does not trigger resize centering. Detailed Layout still rearranges only the shared visible graph. The catalog is bundled into a static site; spoiler protection governs the UI rather than data-access permissions.

`SearchPanel.tsx` owns on-demand discovery query/filter state and the existing bounded, input-edit-only analytics debounce. `searchUpgrades()` matches normalized titles and native effect descriptions, with title matches before effect-only matches and catalog order retained inside each group. `discovery.ts` applies progress-state filters to the shared visible upgrade set and supplies the same `upgradeState()` used by map/details rendering. Owned includes active and awaiting-activation purchases; Available requires both native gates and never infers SP balance. The complete result list scrolls inside the existing Atlas overlay. Rows show an icon, state symbol/text, exact decimal-string cost and effect excerpt; duplicate titles also show their stable ID, determined only from visible upgrades. No hidden identities, counts or topology enter discovery. The search overlay and inputs remain blocked from replay, and filters are session-only view state outside profile backups and undo.

Keyboard result focus scrolls the title into the usable area below the measured sticky count/close header. Actual screen-reader announcements remain unverified; a direct reader session is optional follow-up rather than an acceptance requirement.

## Single-event forward impact

`forward-impact.ts` clones the recorded profile only after validating an explicit currently visible, unowned purchase against both native gates, or an unrecorded visible item milestone. It evaluates that one native purchase/receipt only. It never calls prerequisite filling, activates a lock, performs a reset, writes progress or goals, or adds history. A hypothetical Astral Lock purchase retains the current epoch and remains pending; future activation requires a full reviewed UA transition rather than a flag change or historical correction.

The BEFORE `visibility()` universe governs affected rows, counts and requirement explanations. Affected upgrades reference the chosen stable ID in a purchase or reveal predicate, independent of map edges; owned targets are excluded. Before/after evaluation distinguishes newly eligible purchases, still-blocked alternatives and already eligible OR paths in catalog order. Explicit spoiler browsing additionally explains changed reveal gates and separates reveal-only changes from full eligibility. Default hypothetical reveals contribute no identities, counts or ranking. Read-only requirement projection preserves visible AND/OR grouping and omits hidden leaves and topology.

The optional dialog enters from an auxiliary action AFTER Purchase in expanded details, or from visible unrecorded Milestones. It renders ten rows per group with explicit expansion. Hypothetical controls and results are replay-blocked, make no new analytics calls and have no persistent storage. Closing restores inspection or Milestones; opening generic menus (including null-menu recovery), another preview or purchase closes analysis. Starting analysis invalidates pending file reads. Every actual profile replacement/change or external storage change invalidates the captured analysis before rendering another result. Camera, selection, profile and intention contracts remain unchanged.

Only unowned upgrades from the shared visibility result qualify, and their native reveal and purchase predicates must both be satisfied now. Explicit spoiler browsing does not bypass a native reveal gate. Pending owned Astral locks are excluded from repurchase; eligible new locks carry a delayed-activation note. The engine never fills prerequisites, selects an OR path, changes milestones or applies a reset.

The guide's ascending tier and row order decides priority among eligible mapped IDs. Its earliest non-supplementary occurrence supplies each rank; exact native cost and stable ID break ties. Stage labels describe the source rather than imposing extra epoch/USP requirements. If there are no eligible ranked IDs, the result uses an explicitly labeled exact-cost fallback. It distinguishes every visible upgrade being owned from unowned upgrades blocked by recorded requirements, without counting or naming hidden content.

When no visible purchase qualifies, the dialog offers a requirement-review route to the selected visible blocked upgrade, falling back to visible catalog order. It labels this as a review starting point rather than a suggestion; owned, hidden and native-ready upgrades are excluded.

## Ultra Ascension

`conditionallyRetainedPurchases()` returns only existing purchases whose native retention source is active. `retainedPurchasesOnReset()` evaluates the same conditions after the reset activation phase; `planUltraAscension().conditionallyRetained` lists those existing targets preserved by the planned reset. Ownership comes only from `profile.purchases`, so visibility and recommendations need no separate granted state. The public catalog retains its legacy `grants` field name for compatibility; its four rules never award absent targets.

Ownership, purchase epoch and activation remain independent. A reset activates eligible owned Astral locks, keeps Astrals, retains existing targets of active native retention sources, clears repeat purchases, keeps milestones and advances the epoch. Retention exceptions never award absent upgrades. Each later reset reevaluates the active source conditions. Native source/target pairs and ordering are documented in scripts/logic/README.md. Unknown IDs survive updates and resets because their future rules are unknown.

Upgrade details use the same Astral activation phase to predict conditional retention of existing purchases, including an owned lock that will activate during reset. The explanation uses generic Astral wording without hidden source titles. An absent repeat target is described as unowned and is never granted by the prediction or reset.

Recording prior Ultra Ascensions enters existing history without applying a reset. Editing or leaving the field keeps progress unchanged. **Review history…** validates the draft and opens a confirmation showing the old and new counts; **Record history** applies it. Empty, negative, fractional, decreasing, unchanged and out-of-range entries receive feedback inside Progress, with an accessible invalid-field description. Counts cannot be lowered through that control. Known purchases in the current epoch move to the entered epoch, keeping them current; earlier retained ownership and unknown purchase epochs stay intact. Ownership, activation, milestones and spoiler preference are preserved. Ultra Ascend remains a separate reset preview that clears repeat purchases and activates eligible locks. Undo corrects a history entry in the current session; restoring an earlier JSON backup is the recovery route after reloading. The app does not model SP/USP balances, Stones, Dark Divinity reset overrides or gameplay effects outside this tree.

The version 1 profile continues to accept nonnegative safe-integer epochs through `Number.MAX_SAFE_INTEGER`. Ultra Ascension refuses an increment at that limit before producing a preview, activating locks or clearing purchases. The previous epoch can still advance to the maximum and remain saveable/exportable. Manual history entry and native import retain their existing 1,000,000 entry bound.

Removal and Ultra Ascension previews filter both counts and listed rows through the current shared visibility result. Their unconditional explanation states that confirmation applies to the entire profile; hidden ownership counts, titles and conditional existence are not disclosed. The complete planned profile still supplies every actual change.

## Storage and migration

`saved-comparison.ts` defines a separate version 1 reference document (`kind: upgrade-comparison`, `version: 1`, `ids: string[]`) under `idle-slayer-ascension-map.comparison.v1`. It contains at most four unique bounded stable IDs, no progress, cached catalog facts or notes. Comparison JSON files have a 4 KiB UTF-8 bound and exact-field validation; profile JSON is rejected. Export/restore are explicitly separate from profile backups, native import and session Undo. Unknown IDs survive as unavailable references with no invented identity, rules or cost. Known hidden IDs contribute no row, count, capacity, requirement, picker entry or export. They remain in device storage until a deliberate edit, which preserves only the current visible/unavailable projection; this policy is disclosed constantly rather than revealing hidden existence.

`comparison-session.ts` coordinates only reference-list writes using a separate exclusive Web Lock and exact accepted storage baseline. Clean external updates/clears are adopted without writing back; dirty/pending sessions retain memory and expose explicit use-saved/replace-saved recovery. Corrupt/unreadable storage is never silently overwritten. Held/missing coordination and write failures keep an exportable reference list, with retry/recovery. Version and exact-text guards reject stale confirmation and canceled callbacks. The React hook owns the storage subscription. Dialog close, a newer file request, visibility changes, session changes and unmount invalidate comparison file reads and restore previews. Current visibility is also applied synchronously during render, before effects can clear stale previews.

The optional `SavedComparisonPanel` uses the current shared graph and native requirement projections. Four responsive cards compare arbitrary recorded states, with exact native descriptions, decimal-string costs, stable IDs, current ownership baseline, separate purchase/reveal gates, activation, retention and provenance/version context. The picker searches only visible titles/effects, and a full list requires an explicit replacement or removal. Show on map and requirement review retain the existing inspector/navigation paths without progress mutation; private comparison selection does not emit an upgrade-selection payload. All saved content, picker inputs, restore/recovery summaries and feedback live inside a replay-blocked boundary. No new event or profile field is added.

History entries pair a profile snapshot with a bounded generic action kind. Undo and Redo expose that next action in the footer, Map options and Progress, then announce which snapshot was restored, including the spoiler setting. Labels never contain upgrade or milestone identities, filenames, exact counts or hidden progress. The combined past/future history stays within 20 snapshots; moving between them does not add an action. Any new profile change clears Redo. Reloading and external progress changes clear both stacks and labels. Confirmed adoption of saved progress creates one recovery entry. Undo/Redo use the same pending-write, lock and stored-text checks as other edits, keep failed saves usable in memory, and invalidate pending files/previews before a late read can offer stale replacement. History metadata never enters local storage or portable backups. Redo introduces no analytics event; Undo retains the existing bounded event.

Replacement details use `compareProgress()` and `ProgressComparison` for JSON restore, native import and both conflict-recovery directions. The viewer's current `visibility()` result supplies every listed identity and change count; incoming reveal gates or spoiler choices cannot expand those detailed lists. The existing aggregate import/restore totals continue to evaluate each profile under the current spoiler preference. Detail lists start with ten rows and expand in batches; known activation and ownership-baseline differences remain distinct from UA history. Unknown entries are never enumerated. All comparisons, filenames and snapshot context are excluded from replay. Preview confirmation, stale-session rejection, cancellation, atomic replacement and Undo remain unchanged; the UTC/UA download filename does not add metadata to portable version 1 JSON.

`storage.ts` provides pure backup parsing, export and catalog migration, plus the version 1 key `idle-slayer-ascension-map.profile.v1`. Device persistence belongs to `createProfileSession()` in `profile-session.ts`; application features must use that session so writes retain its locking and conflict checks. There is no standalone profile read/write API. The backup utilities validate exact fields, safe IDs, booleans, and nonnegative integer purchase epochs bounded by the profile epoch. Backups have a 4 MiB limit on both incoming UTF-8 bytes and the canonical indented save/export representation, checked before a restore preview and again after applying the current catalog revision. Catalog migration changes the revision while cloning and retaining every known/unknown purchase and milestone; a migration that exceeds the portable size limit is refused without replacement. No earlier profile schema exists; unsupported versions are rejected. Future schema changes need explicit migrations and round-trip/malformed-input tests.

Read failures report errors without silently deleting stored data. Write failures keep the in-memory session usable and expose retry/export. A reload restores the last successful save; undo is session-only. Clearing all progress requires a preview and remains undoable. Backups contain progress, never saves or Steam metadata.

JSON restore counts use `progress-summary.ts`, shared with native import, to evaluate the incoming profile through `visibility()` under the current map spoiler setting. A backup with spoilers enabled cannot widen its unconfirmed preview. Only recognized visible purchases and recorded visible milestones enter counts; hidden and unknown records are neither counted nor named. Confirmation replaces the entire validated backup profile, including its hidden/unknown records and saved spoiler preference, after applying the current catalog revision. The preview explains this complete replacement without disclosing omitted totals. Cancel leaves the current profile intact, and Undo restores it after applying. Replay exclusions cover the restore summary as before.

Only the latest intended JSON backup read may create a restore preview. Leaving Progress, opening another backup picker, beginning game import, external profile changes and unmount invalidate pending reads; stale successes and failures are ignored. A late file selection outside Progress is ignored. Closing and reopening Progress does not revive a cancelled read. Validation and confirmation still precede replacement.

`profile-session.ts` coordinates every profile write, including undo, restore/import, clearing, retry and saving before a privacy reload. It uses an exclusive Web Lock named `idle-slayer-ascension-map.profile.v1.write`, then compares the exact stored text with the session's last accepted baseline before writing. The version 1 profile, backup fields and storage key are unchanged. Lock acquisition uses `ifAvailable`: held, missing or rejected coordination leaves an exportable memory session with retry instead of an unsafe unlocked write. One operation may be pending; further mutations wait, while navigation, export and privacy controls remain usable. Cancellation invalidates pending callbacks before they can write. Web Locks do not combine `ifAvailable` with an AbortSignal.

Persistence status distinguishes loading, a new session with no saved profile, confirmed saved progress, a pending save, unsaved changes, failed saving/recovery and a cross-tab conflict. A writable storage path does not establish that the current profile was saved. Footer, Map options, About and Privacy share this live status; startup disclosures describe local storage conditionally before progress loads. Existing warnings and retry/export recovery remain available.

Relevant local-storage changes are reread rather than trusting an old event value. A clean session follows a valid external profile or cleared storage without writing it back. Dirty or pending sessions retain their local progress and require explicit conflict recovery; corrupt/unreadable external storage also leaves the session intact. External changes invalidate undo history, OR choices, all previews and pending file reads. Recovery offers export, a confirmed use of readable saved progress, or a confirmed replacement with this session. Both choices recheck the reviewed version and stored text; a newer change requires a fresh review. Adopting saved progress creates one new undo snapshot for that explicit choice. Unknown IDs remain in profiles/backups, and recovery counts use the shared spoiler-visible calculation. A privacy reload promptly offers the existing export/reload/cancel choices when saving is pending or fails.

The coordination guarantee applies to tabs running this implementation. After deploying it, manually reload any previously open tabs so older code cannot continue making uncoordinated writes.

## Steam save import

`save-codec.ts` reads only user-selected bytes, applies the reviewed UTF-16 XOR transport and validates the complete typed native model within a 4 MiB limit. Keys may repeat across native preference types but not within one array. `game-save-import.ts` requires native version 7.2.0, maps recognized stable IDs and the native UA count, and discards every unrelated preference. `data/save-import-receipt.json` records sanitized offline native evidence; [save-import.md](save-import.md) defines compatibility, mappings and refresh checks.

The importer creates a replacement snapshot without filling dependencies, selecting OR paths, inventing milestones or granting absent targets. Pending locks stay pending. Active Astrals and existing targets of active retention sources use a synthetic earlier-epoch baseline when the imported UA count is positive. The native save has no purchase timestamps, so this policy protects current retained ownership during later map edits without claiming to reconstruct history. Existing unknown map IDs remain; epochs above an older incoming counter are clamped with an explicit warning. Spoiler preference stays unchanged.

Progress opens the native file picker. A separate preview uses the shared visibility calculation for comparison counts and shows the incoming UA count and import notes. Apply uses normal history and validated storage; cancel, read failures and malformed inputs leave progress unchanged. Cancellation invalidates asynchronous reads so late completion cannot reopen or apply a stale snapshot. Applying an import also explicitly replaces inaccessible/corrupt map storage, like JSON restore; a write failure still leaves the session usable. Raw bytes and decoded native preferences never enter local storage, backups, logs or network requests. The game file remains read-only, and the importer has no automatic directory access or cloud login.

## Usage analytics and session recording

The static app loads the authorized self-hosted Umami tracker and recorder through a separate analytics boundary. UI handlers emit typed, bounded events; pure game rules, save decoding and profile persistence do not perform tracking. Loading, storage and import failures use fixed categories rather than arbitrary messages. Automatic camera recentering is not a user event, and overlapping React Flow selection callbacks must produce one semantic selection.

Tracking starts only after a separate preference read succeeds and permits it, and browser privacy signals are respected. The opt-out is not part of `Profile`, JSON backups or undo history; resets and restores cannot enable tracking. Preference read failures keep tracking off. Changing the preference reloads to stop recorder observers and network activity. If profile saving fails first, the user chooses export-and-reload, reload without backup or cancel. A failed tracking-preference write reloads with `#analytics=off`; keeping/bookmarking that URL preserves the visit opt-out without representing it as a persistent storage preference. Reloading clears session-only undo normally.

Recordings can capture the rendered visible map, upgrade states and ordinary interaction. Search text, file inputs, UA-counter inputs, save-import and JSON-restore previews, and raw error details are excluded from replay contents before the recorder initializes. Selected files and unrelated native preferences never enter event payloads or replay DOM. Replay blocking does not suppress the recorder's coarse heatmap click/scroll coordinates, and iframe recording is disabled. URLs are canonicalized and arbitrary queries/hashes are removed; campaign values follow the bounded allowlist in [analytics.md](analytics.md).

Analytics is an optional external service: script, network and API failures must leave every map feature usable. Local/CI browser checks intercept analytics requests and validate payloads and exclusions without contacting production. [analytics.md](analytics.md) is the operator guide and event/report contract.
